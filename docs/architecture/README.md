# Архитектура и решения

## Текущее состояние

Проверено по исходникам на исходном HEAD `56f8be0`:

- React/TypeScript интерфейс расположен в `jarvis-app/web`.
- `server.mjs` соединяет HTTP API, Telegram, Moodle, расписание, журнал и фоновые задачи.
- `users.mjs` содержит конкретный адрес Moodle МИСИС и файловое хранение доступа.
- `useAppStore.ts` знает `MoodleResponse` и правила идентификаторов Moodle.
- `official.mjs`/`schedule.mjs` получают расписание отдельно от LMS;
  `course-sheets.mjs`/`sheets.mjs` обрабатывают таблицы.

Это описание исходной версии, не обещание работы в новом окружении. Ранее
хранившийся рядом с runtime ключ не является целевым способом управления
секретами новой версии.

## Целевая версия

Направление принято в [ADR-0001](../adr/0001-preserve-ui-replace-backend.md).
Предлагаемая схема и открытые решения находятся в
[RFC-0001](../rfcs/0001-multi-university-platform.md).
Проверяемое поведение — в [FR/NFR](../product/requirements.md).
Для клиентской дизайн-системы действует отдельный
[RFC-0002](../rfcs/0002-design-system.md): он предлагает границы модели маскота,
renderer, событий и UI-kit. [Дизайн-навигатор](../design/README.md) связывает
требования с задачами по коду и владельцами файлов.

## Когда нужен документ

| Изменение | Ожидаемая запись |
|---|---|
| Исправление внутри известного контракта | Задача/PR с поведением и проверкой |
| Новая граница компонента, схема, модель доступа, значимый API | Короткий RFC с альтернативами и переходом |
| Принятое существенное решение | ADR со ссылкой на обсуждение/RFC |
| Изменение согласованного поведения | Обновление FR/NFR и проверок |

RFC не является обязательным ритуалом для каждой правки и не добавляет отдельное
согласование к уже разрешённой задаче. При экстренном исправлении запись может
сопровождать PR; не откладывай восстановление ради оформления документа.

## Статусы и нумерация

RFC: `Draft` → `Proposed` → `Accepted` / `Rejected` / `Superseded`.
ADR: `Proposed` → `Accepted` / `Rejected` / `Superseded`.
Номер — следующий свободный четырёхзначный номер в соответствующем каталоге;
после публикации не переиспользуется. При параллельной работе согласуйте номер.

Указывай отдельно состояние реализации: `not started`, `partial`, `implemented`,
и подтверждение проверок. Изменение статуса согласуется в задаче/PR с владельцем
решения; агент не придумывает одобрение из собственного текста.

Принятое решение не переписывай незаметно задним числом. Если изменилось
основание, создай новый ADR и свяжи записи через `Supersedes`/`Superseded by`.
Шаблоны: [RFC](../templates/rfc.md), [ADR](../templates/adr.md).
