# Проверки и доказательства

Статус: политика командной разработки и границы CI. Новый backend имеет отдельные
platform fixtures для пространств, discovery, auth, jobs и retrieval. Они не
доказывают live SSO и не переводят автоматически legacy frontend на v1.

## Уровни

| Уровень | Команда | Что доказывает | Чего не доказывает |
|---|---|---|---|
| Статический | `npm run check`, `npm run typecheck` | Применимый синтаксис, типы, локальные ссылки документов | Исполнение приложения и корректность вузовского API |
| Unit | `npm run test:unit`, `npm run test:web` | Выбранные функции преобразования и локальные правила на синтетических входах; `test:web` — чистые TS-модули Mini App | Связку сервисов и живые данные |
| Integration | `npm run test:integration` | Контракты выбранных модулей, файлы состояния, доступ и отказ поддельных сервисов | Живой SSO, реальное расписание и доставку Telegram |
| Platform | `npm run test:platform` | SQLite, ACL 2×2, crypto, Telegram HMAC, jobs/fencing/restart, SSRF, OAuth/refresh и retrieval/chat | Живые вузовские аккаунты и ответы настоящей модели |
| Browser smoke | `npm run build`, `npm run test:e2e` | Запуск собранного UI и выбранные действия пользователя с fixture API | Полный production E2E или новую многовузовскую архитектуру |
| Chromium runtime | `npm run test:chromium` | Запуск Chromium с sandbox, рендер `data:`-страницы и кадр CDP screencast без внешней сети | Вход в вуз, SSO/MFA и стабильность долгих сессий |
| Live acceptance | Отдельный согласованный сценарий | Конкретный разрешённый аккаунт/источник в зафиксированное время | Все роли, факультеты, вузы и бессрочную работоспособность |

`npm run ci` последовательно запускает обязательный автоматический набор.
Установка описана в [DEVELOPMENT.md](DEVELOPMENT.md). Точный состав suites задаёт
репозиторный runner; не добавляй исторический тест в CI без проверки его эффектов.

Текущий [каталог](../scripts/test-catalog.mjs) включает восемь unit-suites
(`admission`, `moodle-plan`, `attendance`, `calendar`, `cal-tunnel`, `ratelimit`,
`tunnel-url`, `tunnel-mainapp`) и восемь integration-suites (`pace`, `sheets`,
`course-sheets`, `ej-cred`, `deadlines-disk`, `tg-retry`, `consent`, `purge`).
Браузерные фикстуры проверяют вход/данные/повторное открытие, отказ неверных
учётных данных и отображение сохранённых данных при недоступном источнике.
Это выбранное покрытие существующего приложения; не список всех его проверок.

## Что проверять в изменении

- **Исправление дефекта:** наблюдаемый сбой и результат после исправления;
  предпочтителен регрессионный сценарий, который падал до изменения.
- **Парсер/адаптер:** минимальная редактированная фикстура, нормальный и неполный
  ответ, пагинация, изменения структуры и неподдержанный формат.
- **Авторизация и секреты:** неверная/старая идентичность, подмена пользователя,
  пространства, подключения и ID; не тот ключ/контекст шифрования; отсутствие
  plaintext в ответах, логах и запросах к модели.
- **Sync:** повтор, одновременный запуск, timeout, истечение доступа, 403, 429,
  частичный ответ, перезапуск и сохранение последнего успешного снимка.
- **UI:** основной путь и ошибка, пустое/устаревшее состояние; браузерная проверка
  для изменённых важных взаимодействий и проверка на узком экране.
- **Чат/retrieval:** разрешённое пространство, происхождение фактов, свежесть,
  отсутствие источника, противоречие, недоверенные инструкции в документе;
  личный контекст не попадает в общий FAQ.
- **Текстовая правка:** проверить ссылки и применимые статические правила;
  не писать бессодержательный тест, повторяющий текст файла.

Источники вузов (`backend/test/universities.test.mjs`): iCal-разбор, РУЗ, Moodle за SSO, секретный feed-URL и HTTP-формы входа
проверены на синтетических фикстурах; формат ответа РУЗ и реальные ответы `edu.hse.ru` остаются live-приёмкой владельца.

Сессионный sync (`backend/test/learned*.test.mjs`, `session-sync*.test.mjs`, фикстуры `backend/test/fixtures/session-sync`): настоящий `createSafeRequest` в режиме сессии поверх loopback-сервера — lint личных данных,
обучение рецепта, sync двух пользователей по общему рецепту, протухание (401, редирект на логин, HTML-форма, `servicerequireslogin`, `expiresAt`), сбой формата и откат, Moodle AJAX seed и агент с инъекцией из страницы.
Seed ЦУ/ВШЭ и поведение живого SSO этим не подтверждены.

Критичные platform-сценарии: два пользователя × два пространства; общая версия
адаптера при разных сессиях; одинаковые внешние ID двух источников; отключение
подключения во время sync; удаление записи из памяти и поискового индекса.
Они проверяются в `backend/test`; frontend cutover и live интеграции остаются
отдельными критериями приёмки.

Браузерный набор дополнительно открывает каталог маскотов на dev-сервере Vite (порт `14174`,
меняется через `E2E_CATALOG_PORT`) и проверяет огонь, бейджи, однократную реакцию и reduced motion.

`tests/e2e/spaces.spec.mjs` проверяет режим нового API на синтетическом `/api/v1`: два вуза,
переключение без данных прежнего, ошибку обновления с сохранёнными данными и подключение вуза.

`tests/e2e/universities.spec.mjs` (задача C, ADR-0005) проверяет экран «Вузы» (`#/universities`) на синтетическом `/api/v1` с WebSocket
(`fixtures/universities.mjs`): четыре раздела с предзаполненными источниками; вход через удалённый браузер (тикет, кадры, мышь,
клавиши, текст, переподключение с новым тикетом, касание и колесо); пароль + MFA (попытки, ручной переход в браузер); токен, пароль Moodle
и ссылка календаря; отказ старта (`LOGIN_COOLDOWN`), сервер без Chromium; ошибки словами с кодом; устаревшие данные; «Войти снова».
Скриншоты разделов пишутся в `artifacts/screenshots/`. Это поведение UI по контракту, не живой Chromium и не вход в вуз.

`tests/e2e/motion-a11y.spec.mjs` (DES-009, зона A): reduced motion и спокойный маскот (огонь-знак без
анимации, выбор сохраняется), пауза на скрытой вкладке, фокус с клавиатуры на переключателе вуза и
действии маскота, ни один элемент экранов вузов не выходит за ширину 320/390/768 px и 195 px
(390 px при масштабе страницы 200 %) с длинным русским текстом, `aria-live` не объявляет отсчёт.
Экранный диктор и настоящий телефон этим не проверяются.

`tests/e2e/connect-hse.spec.mjs` — подключение ВШЭ на синтетическом `/api/v1`: Smart LMS ссылкой
календаря и логином (с пометкой про SSO), РУЗ по идентификатору и отказ вне сети ВШЭ.

Web unit-тесты лежат в `jarvis-app/web/tests/*.test.mjs` и запускаются через
`node --test` с загрузчиком `scripts/web-ts-hooks.mjs` (Node сам убирает типы;
допустим только стираемый синтаксис TypeScript). В CI они идут в задаче
`Web build and browser fixtures` после typecheck.

Дизайн-задачи проверяются по [DS-критериям](design/requirements.md) и
[DES-001–DES-012](design/tasks.md). Чистая модель маскота требует unit-проверок
clock/дат, приоритетов, смены пространства, stale и reduced/lite. Renderer/UI-kit
проверяются на детерминированных фикстурах в обеих темах, узком viewport,
с длинным текстом, focus и клавиатурой. Сезонность тестируется на фиксированных
границах декабря/января, независимо от даты запуска CI.

Скриншоты получают из контролируемого браузера с остановленным движением;
изменение baseline требует просмотра причины diff. Визуальное совпадение не
заменяет проверку текста/CTA/семантики, контраста, screen reader или целевого
устройства. Новый каталог/сценарии ещё предстоит реализовать в DES-задачах;
текущие три browser smoke-сценария их автоматически не покрывают.

## CI и внешние системы

[Workflow CI](../.github/workflows/ci.yml) запускается для pull request, push в
`main` и вручную. Проверки: `Source and documentation checks`,
`Backend / unit fixtures`, `Backend / integration fixtures`,
`Web build and browser fixtures`, `Platform security and workflow fixtures`. Actions закреплены на commit SHA, доступ к
репозиторию — только чтение; checkout не сохраняет Git credentials.
Синтетические отчёты и браузерные traces хранятся как артефакты семь дней.
Включение required checks в защите ветки — отдельная настройка GitHub, этот
workflow сам её не меняет. Браузерный gate отклоняет пустой отчёт и пропуски.

GitHub Actions использует синтетические данные и не требует university-,
Telegram- или LLM-секретов. Pull request не получает production-доступа, не
отправляет сообщения, не начинает тесты в LMS и не публикует приложение.
Запуск модели и сетевой поиск не нужны для детерминированной проверки её tools.

Фикстуры не содержат реальные имена, оценки, cookies, пароли, CSRF или подписанные
ссылки. Захват реального ответа сначала очищается и сокращается; пользовательское
разрешение на просмотр не означает разрешение опубликовать его в Git.

Сбойный тест оставляет минимальные отчёты/диагностику без секретов. Пропуск или
отсутствующий браузер/интерпретатор не считаются успешной проверкой. Не добавляй
`continue-on-error`, безусловный `|| true` или автоматический retry, скрывающий
воспроизводимый сбой. Flaky-сценарий получает причину, владельца и задачу на
исправление; снятие обязательной проверки не заменяет исправление.

## Известные границы

Часть прежних тестов содержала абсолютные Windows-пути; полный старый Windows/
OpenClaw runtime и все эксплуатационные сценарии не входят в переносимый набор.
Browser smoke не подтверждает телефонный клиент Telegram, MFA/CAPTCHA, сеть
вуза, протухание реальной сессии или доступность ВШЭ/МИСИС. Для них нужны
отдельные разрешённые проверки; фиксируй сценарий и пробел в PR.

При финальной приёмке новой интеграции запиши дату, источник, роль аккаунта,
перечень прочитанных данных, исходную ссылку, повторное открытие и известные
ограничения. Не прикладывай креды, личную выгрузку или полный браузерный профиль.
