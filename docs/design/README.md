# Дизайн-система и задачи команды

Статус: **постановка работ**, 2026-10-25. Реализация нового набора требований
ещё не начата. В репозитории уже есть токены, светлая/тёмная темы и сова;
их наличие не означает выполнение критериев ниже.

Если человек спрашивает «Какие у нас задачи по дизайну?», начни с этой страницы
и [списка задач](tasks.md). Назови владельца зоны, ID, приоритет, зависимости,
критерии готовности и ближайшую свободную задачу. Не выдавай план за готовый код.

## Две самостоятельные инженерные зоны

| Зона | Ответственность | Результат в продукте |
|---|---|---|
| **A — маскот и поведение**; участница, которая занимается совой | Состояния, renderer, огонь дедлайнов, события и сезонные образы, управление движением, тесты логики | Одна узнаваемая сова объясняет состояние приложения и реагирует на реальные данные |
| **B — основы и компоненты**; участница, которая занимается презентацией | Визуальное направление, токены, UI-kit, состояния компонентов, каталог, доступность, визуальные проверки | Единый качественный интерфейс и проверяемые компоненты; презентация использует ту же систему |

Это задачи по коду, а не только подготовка картинок или слайдов. Зоны работают
параллельно с отдельным участником frontend: он владеет экранами, навигацией,
пространствами вузов, API-клиентом и интеграцией. Владелец backend отвечает за
авторизацию, источники, нормализацию и retrieval. ВШЭ и МИСИС — первые вузы.

## Что читать

- [Требования](requirements.md): направление, токены, компоненты, сова,
  события, доступность и проверяемые ограничения.
- [Контракты](contracts.md): входы маскота, независимые слои, права на файлы
  и передача результата frontend без доступа к backend/секретам.
- [Задачи DES-001–DES-012](tasks.md): приоритеты, зависимости, код и приёмка.
- [RFC-0002](../rfcs/0002-design-system.md): предложенное устройство и переход.
- [FR/NFR](../product/requirements.md): связь с поведением продукта.
- [Проверки](../TESTING.md) и [разработка](../DEVELOPMENT.md): действующие команды.

## Первый общий результат

1. Зафиксировать короткое визуальное направление и границы файлов (DES-001).
2. Параллельно начать токены/UI-kit (B) и чистую модель состояния совы (A).
3. Показать компоненты и сову на синтетических состояниях без готового backend.
4. Передать frontend типизированные props и согласованные примеры состояний.
5. Проверить узкий экран, обе темы, reduced motion, ошибку и переключение вуза.

Сезонные украшения, например новогодняя шапочка, добавляются отдельным слоем.
Они не заменяют функциональные состояния, не скрывают ошибки и не меняют данные.

## Статусы и работа с агентом

Задача переходит `planned → in_progress → review → done`. При взятии укажи имя,
ветку/PR и принадлежащие задаче файлы в [реестре](tasks.md). Вопрос о дизайне сам
по себе не разрешает агенту начать случайную реализацию: сначала вернуть список
готовых к старту задач. Явный запрос реализовать выбранную задачу разрешает
обычные обратимые шаги внутри её границ; дополнительных ритуалов не нужно.

Не меняйте общие токены, renderer и экраны одновременно в разных ветках без
назначенного владельца. Каждая задача заканчивается кодом/описанием,
синтетическим примером, применимыми проверками и честным состоянием готовности.
