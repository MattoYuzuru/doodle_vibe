# ADR-0005: вход через удалённый браузер, зашифрованная сессия и выученные рецепты

- Статус: Accepted — решение владельца, переданное координирующей сессией 2026-10-25 (цитата ниже); подтверждение владельца в чате исполнителя не получено, перед использованием в проде сверить.
- Дата и основание принятия: 2026-10-25. Владелец: «SSO-вход через headless-браузер, MFA из UI, хранить только зашифрованную сессию без пароля, agent retrieval поверх сессии, подключить UI к /api/v1» и «универсальный вход в любой вуз через удалённый браузер: пользователь входит сам любым способом (SSO, MFA, капчу решает человек), сессия и токены попадают в приложение; вуз изучается один раз, дальше все синкаются по рецепту».
- Реализация: not started — этот ADR и [контракт](../architecture/auth-sessions-contract.md) фиксируют границы; код делят три параллельные задачи A/B/C из контракта.
- Связанные FR/NFR, RFC и issue: FR-004, FR-007, FR-008, FR-009, FR-012, NFR-002–NFR-006, NFR-012; [ADR-0002](0002-isolated-sqlite-backend.md), [ADR-0004](0004-universal-source-types.md).
- Supersedes / Superseded by: уточняет ADR-0004 п. 6 и `docs/universities.md` («SSO/MFA не автоматизируется»): SSO по-прежнему не обходится, но его проходит **человек в удалённом браузере** (или сервер по паролю, который человек ввёл сам). Защита от ботов и CAPTCHA не обходятся.

## Контекст

Многие вузы (ВШЭ — Keycloak `saml.hse.ru` за OIDC, ЦУ `my.centraluniversity.ru` и др.) не дают токена студенту, а вход — SSO с MFA и
иногда CAPTCHA. Ссылка календаря (ADR-0004) покрывает только дедлайны. Нужен один механизм для любого вуза и без релиза на каждый.

## Решение

1. **Менеджер login-сессий** (серверный Chromium): пользователь выбирает вуз, Mini App показывает кадры удалённого браузера
   (CDP screencast) и отправляет обратно мышь и клавиатуру; вход выполняет человек любым способом, капчу решает человек.
   Тот же менеджер имеет **режим пароля**: сервер сам заполняет форму по пресету (ВШЭ), код MFA вводится из UI. Один
   активный контекст на пользователя, жёсткие TTL и лимиты — в контракте.
2. **Сохраняется только зашифрованное состояние сессии**: cookies разрешённых хостов и извлечённый bearer (JWT/токен из
   `localStorage`/`sessionStorage` или заголовка `Authorization` в XHR). Пароль, код MFA, нажатия клавиш, кадры, HTML и
   скриншоты не хранятся и не логируются. Секрет — в существующей таблице `secrets` (AES-256-GCM, AAD пользователь/пространство/подключение).
   Схема SQLite не меняется.
3. **Изучение вуза один раз**: во время входа и просмотра исполнитель наблюдает XHR/fetch **только в памяти** и строит
   **выученный рецепт v2** — декларативный, общий на origin, без личных данных, только чтение (GET или явный read-only POST из
   списка). Рецепт проходит lint и canary на сессии того, кто его выучил, версионируется и откатывается. Дальше все
   пользователи вуза синкаются по рецепту со **своими** токенами.
4. **Протухание**: 401/403, редирект на логин или признак истёкшего токена → `user_action_required` + `source_session_expired`;
   прежние снимки сохраняются; плановый sync не создаёт попыток входа.
5. **Agent retrieval** — резерв там, где нет рецепта: только GET, только origin источника, секретов LLM не видит, текст страниц — данные.
6. **Dev-авторизация без Telegram** — только по явному флагу, loopback, синтетический пользователь; в production отказ при старте.

## Альтернативы

- Хранить пароль зашифрованным — шире поверхность утечки; отклонено владельцем.
- Принимать cookies из браузера пользователя — не работает внутри Mini App и переносит риск на пользователя.
- Маршрутизация Playwright как единственный allowlist — `route.continue` **не видит серверные редиректы** (проверено на Chromium 1228+:
  редирект с разрешённого хоста на чужой не блокируется); allowlist держит фильтрующий CONNECT-прокси.
- Обход QRATOR/CAPTCHA, stealth-плагины — запрещены.

## Последствия и проверка

- Сервер видит нажатия клавиш и содержимое экрана пользователя во время входа (пароль, MFA, CAPTCHA). Смягчение — память, TTL,
  изоляция контекста, отсутствие логирования; остаточный риск принят владельцем: оператор сервиса технически способен прочитать токены в памяти процесса.
- Прод: Chromium, память, `/dev/shm`, непривилегированный пользователь, исходящий HTTPS только к хостам пресетов — см. раздел «Рантайм» контракта. Деплой в mnema этим ADR не выполняется.
- Каждая задача A/B/C проверяется своими фикстурами: поддельные Keycloak/Moodle/SPA с JWT на loopback (HTTPS + настоящий Chromium), SSRF-редирект,
  grep БД/логов на пароль и код, рецепт без личных данных, отказ при истёкшей сессии. Живой вход делает владелец сам.
- Не подтверждено вживую: страница MFA ВШЭ, поведение QRATOR для удалённого браузера, срок жизни `MoodleSession`, формат API ЦУ.
